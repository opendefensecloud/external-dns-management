## Project Overview

**external-dns-management** is the Gardener DNS Controller Manager - a Kubernetes controller that manages DNS records across multiple DNS providers. It's part of the Gardener project ecosystem.

The project provides two implementations:
- **compound** (classic): Built on `controller-manager-library`, supports all providers including Infoblox and Remote
- **nextgen** (dnsman2): Controller-runtime rewrite that queries authoritative nameservers directly instead of provider APIs, reducing API rate limit issues. Does not support Infoblox or Remote providers.

## Architecture

### The Model - Three-Tier Architecture

```
Source Resources          DNSEntry (decoupling)        DNS Providers
(Services, Ingress,   →   (Custom Resource)      →    (Route53, CloudDNS,
 Gateways)                                              Azure, Hetzner, etc.)
```

**Key Concepts:**

1. **Source Controllers**: Watch Kubernetes resources (Service, Ingress, Gateway) with DNS annotations and create `DNSEntry` objects
   - Location: `pkg/controller/source/`
   - Types: service-dns, ingress-dns, istio-gateways-dns, k8s-gateways-dns

2. **DNSEntry**: Central custom resource that decouples DNS source from provisioning
   - Explicitly created by users OR automatically generated from annotated resources
   - Contains: DNS name, TTL, targets (IPs or CNAMEs), provider selection

3. **Provisioning Controllers**: Watch `DNSEntry` objects and reconcile with DNS providers
   - Location: `pkg/controller/provider/`
   - Each provider type (aws-route53, google-clouddns, etc.) implements `DNSHandler` interface
   - Compound controller aggregates all provider implementations

4. **DNSProvider**: Specifies credentials, zones, and domain filters for a DNS backend
   - Multiple providers can coexist
   - Dynamically managed (add/update/delete without controller restart)

5. **DNSAnnotation**: Allows injecting DNS annotations into resources without modifying them directly
   - Useful when resources are generated by Helm or other controllers

### Multi-Cluster Support

Three logical clusters (can map to same physical cluster):
- **default/source**: Where annotated resources (Services, Ingresses) exist
- **target**: Where `DNSEntry` objects are created and managed
- **provider**: Where `DNSProvider` objects and secrets exist

In Gardener's shoot/seed architecture:
- Source = shoot cluster
- Target = seed cluster (shoot namespace)
- Provider = seed cluster (shoot namespace)
- Runtime = seed cluster (where controller runs)

### Classic vs Next-Generation

**Classic (compound)**:
- Uses `controller-manager-library`
- Caches DNS zone state from provider APIs
- Supports all providers including Infoblox and Remote
- Entry point: [cmd/compound/main.go](cmd/compound/main.go)
- Package: `pkg/controller/`, `pkg/dns/`

**Next-Generation (dnsman2)**:
- Uses `controller-runtime` (standard Kubernetes controller framework)
- Queries authoritative nameservers directly via DNS protocol
- Eliminates zone state caching, reduces provider API calls drastically
- No Infoblox or Remote provider support
- Entry point: [cmd/nextgen/main.go](cmd/nextgen/main.go)
- Package: `pkg/dnsman2/`
- Documentation: [docs/dnsman2/](docs/dnsman2/)

## DNS Provider Implementation

### Adding a New Provider (Classic)

1. Create provider package in `pkg/controller/provider/<name>/`
2. Implement `provider.DNSHandler` interface:
   - `GetZones()`: List managed zones
   - `GetZoneState()`: Get current DNS records
   - `ExecuteRequests()`: Apply DNS changes
   - `Release()`: Cleanup
3. Create factory implementing `provider.DNSHandlerFactory`
4. Register factory with compound factory in `factory.go`
5. Create controller subpackage if needed for standalone usage
6. Add anonymous import in [cmd/compound/main.go](cmd/compound/main.go)

Example: [pkg/controller/provider/aws/](pkg/controller/provider/aws/)

### Adding a New Provider (Next-Gen)

1. Create provider package in `pkg/dnsman2/dns/provider/handler/<name>/`
2. Implement required files:
   - `factory.go`: Provider registration and credential validation
   - `handler.go`: Implement `provider.DNSHandler` interface (GetZones, ExecuteRequests, GetCustomQueryDNSFunc, Release)
   - `client.go`: HTTP client for provider API (with rate limiting, retry logic)
   - `execution.go`: Change execution logic (CREATE, UPDATE, DELETE operations)
3. Add comprehensive unit tests with Ginkgo + Gomega (target: 85%+ coverage)
4. Register provider in [pkg/dnsman2/controller/controlplane/dnsprovider/add.go](pkg/dnsman2/controller/controlplane/dnsprovider/add.go)
5. Add provider documentation in `docs/<name>/README.md`

Example implementations: [pkg/dnsman2/dns/provider/handler/hetzner/](pkg/dnsman2/dns/provider/handler/hetzner/), [pkg/dnsman2/dns/provider/handler/aws/](pkg/dnsman2/dns/provider/handler/aws/), [pkg/dnsman2/dns/provider/handler/google/](pkg/dnsman2/dns/provider/handler/google/)

## DNS Classes

Multiple DNS controller sets can coexist in same cluster using DNS classes:
- Annotation: `dns.gardener.cloud/class`
- Default class: `gardendns`
- Gardener shoot delegation: `garden`

Controllers only process resources matching their configured DNS class.

## Remote Access

The compound controller can expose a remote access server allowing other DNS controllers to delegate to it:
- Uses gRPC with mutual TLS
- Configuration: `--remote-access-port`, `--remote-access-server-secret-name`
- Remote provider type connects to this server
- Implementation: [pkg/server/remote/](pkg/server/remote/)
